# Contract: Internal Hop Headers and Envoy Configuration

These headers and Envoy settings are **gateway-internal**. None of them reach the client or a real provider.

## Request flow

```text
client ──► FRONT HOP (LlmProxy route, main listener)
             ext_proc: user policies + model-failover[role=front]  (runs once)
             router:   retry_policy ──► cluster failover_dispatch (internal_upstream)
                                              │  one request per attempt
                                              ▼
           DISPATCH HOP (internal listener, route matched by x-wso2-failover-chain)
             ext_proc: model-failover[role=dispatch] → transformer(target) → loopback-auth(target)
             lua:      base-path rewrite for the selected per-target upstream
             router:   cluster_header x-target-upstream ──► upstream_LlmProxy_<id>_failover-t<k>
                                              │  loopback 127.0.0.1:<listener>
                                              ▼
           PROVIDER HOP (existing LlmProvider route, unchanged) ──► real provider
```

## Headers

| Header | Set by | Removed by | Value / rule |
|---|---|---|---|
| `x-wso2-failover-*` (any, from the client) | — | Front `model-failover` (`HeadersToRemove`); the plan header is overwritten | Always stripped from client requests (anti-spoofing). This can't be done in route config: a route's `request_headers_to_remove` runs after ext_proc and would also strip the plan header. |
| `x-wso2-failover-chain` | Front route `request_headers_to_add` | Dispatch route | `chainId`. The dispatch route matches on it. |
| `x-wso2-failover-plan` | Front `model-failover` | Dispatch `model-failover` | 32 hex chars. An unknown or expired nonce, or a chain mismatch, gets a non-retriable 500 and is logged. |
| `x-wso2-failover-hop` | Dispatch `model-failover` | Client-facing listener's `wso2.failover.hop` Lua filter, which moves it into dynamic metadata `wso2.failover/hop` before the router, so it is **never forwarded to a provider** | Per-boot secret from the controller. |
| `x-wso2-upstream-failure` | HCM `local_reply_config` mapper | Dispatch `model-failover` | `%RESPONSE_FLAGS%`. Maps to reasons: UF/URX/UH/LR → `connect_failure`; UC/DC → `reset`; UT/UO → `timeout`. |
| `x-wso2-failover-retry` | Dispatch `model-failover` (eligible failure) | Front `model-failover` and front route `response_headers_to_remove` | Reason string. Envoy `retriable_headers` matches on presence. |
| `x-wso2-failover-exhausted` | Dispatch `model-failover` (cursor past end of plan) | Front `model-failover` | `true`. The response status is 500 and it is untagged, so it is not retried. |

## Front route: Envoy settings generated by the controller

```yaml
route:
  cluster: failover_dispatch                 # fixed; no cluster_header on the front route
  timeout: max(configured, n * perAttemptTimeout + 2s)
  retry_policy:
    retry_on: "retriable-headers,connect-failure,reset"   # drop reset when failoverOn.timeout=false
    num_retries: n - 1
    per_try_timeout: perAttemptTimeout      # stops once response headers arrive
    retriable_headers: [{ name: x-wso2-failover-retry, present_match: true }]
    retry_back_off: { base_interval: 0.001s, max_interval: 0.010s }
request_body_buffer_limit: router.failover.max_request_body_bytes     # Route-level field; default 4 MiB
request_headers_to_add: [{ header: { key: x-wso2-failover-chain, value: <chainId> }, append_action: OVERWRITE_IF_EXISTS_OR_ADD }]
request_headers_to_remove: [x-target-upstream]
response_headers_to_remove: [x-wso2-failover-retry, x-wso2-failover-exhausted, x-wso2-upstream-failure]
```

The `failover_dispatch` cluster uses the internal listener as its address and sets `circuit_breakers.thresholds.max_retries` to 1024 or more.

**When `failoverOn.timeout` is `false`**: the controller drops `reset` from `retry_on`. `per_try_timeout` is still set, and the timeout becomes Envoy's final `504` local reply, passed through to the client unchanged. Eligible statuses and transport failures are still retried through `retriable-headers` (spike S2h/S2j).

## Dispatch route

- Mirrors the proxy route's context and path semantics.
- Matches `prefix: "/"` plus header `x-wso2-failover-chain == <chainId>`.
- Uses `cluster_header: x-target-upstream`.
- Route timeout is disabled (`0s`). The front hop's `per_try_timeout` owns attempt timing, and the idle timeout is kept.
