# Phase 0 Research: Upstream Retry Contribution

All unknowns below were resolved by direct investigation of the current `gateway-controller` codebase, not assumption. No `NEEDS CLARIFICATION` markers remain in the plan's Technical Context.

## Decision 1: Where `RetryPolicy` is built today, and why it can't just be "always on"

**Decision**: The merge-and-build step for the route's `RetryPolicy` must live at the same call-site `translator.go` already uses, broadened from `if rdcRoute.Upstream.Failover != nil` to `if rdcRoute.Upstream.Failover != nil || len(rdcRoute.Upstream.RetryContributions) > 0`.

**Rationale**: Confirmed in `pkg/xds/translator.go` (~line 401): `routeAction.Route.RetryPolicy` is constructed exactly once, inside the `model-failover`-specific gate, nowhere else. A route with any other policy attached — oauth2-generator included — gets no `RetryPolicy` object at all today, so Envoy has nothing to retry on regardless of status code. This single call-site is also where `RetryOn`/`RetriableStatusCodes`/`NumRetries`/`PerTryTimeout` are already assembled from `rdcRoute.Upstream.Failover`'s fields — the natural seam to extend rather than duplicate.

**Alternatives considered**: A second, independent `RetryPolicy`-building code path for the non-failover case — rejected, since Envoy's route config has exactly one `RetryPolicy` slot; two independent builders would have to merge their outputs anyway, so building one generic merge in the one existing location is strictly simpler and avoids a second place that can drift from the first.

## Decision 2: How the policy-definition-level contribution reaches the translator

**Decision**: Resolve `upstreamRetryOn` contributions during the **transform** phase (where `model-failover`'s own `applyModelFailoverPolicyToRoutes` already runs, in `pkg/transform`), not inside the xDS translator itself. The transform step writes the resolved contributions onto a new generic field on the `Route` model — `Route.Upstream.RetryContributions []UpstreamRetryContribution` — which the translator then reads generically, the same relationship `RouteFailover` already has with `translator.go`.

**Rationale**: Traced the only existing path from "loaded policy definitions" to "code that runs per route." `utils.PolicyLoader.LoadPoliciesFromDirectory` is called exactly once, at controller startup (`cmd/controller/main.go:319`), and its result flows into `utils.NewLoadedPolicyVersionResolver(policyDefinitions)` — a `PolicyVersionResolver` already held by `transform.LLMTransformer` (`pkg/transform/llm.go`) and used throughout that package to resolve a policy name to its version (`resolvePolicyVersion`). Grepping `pkg/xds` and `pkg/policyxds` for `PolicyVersionResolver` returns zero results: policy definitions are **not** currently reachable from the xDS/translator layer at all. The transform layer is therefore the only place in the existing pipeline that already has both "which policies are attached to this route" and "access to policy definitions" at the same time — exactly mirroring how `model-failover`'s own detection-and-population step already works.

**Alternatives considered**:
- *Thread `policyDefinitions` (or a resolver) directly into the xDS translator.* Rejected: would be new plumbing with no existing precedent, duplicating what the transform layer already has, and would blur the established boundary (transform = "what does this attachment mean", xds = "emit Envoy config from already-resolved facts") that `RouteFailover` already relies on.
- *Have each policy's own Go code report its retry needs at runtime (e.g., via the SDK), rather than a static declaration read at deploy time.* Rejected: a retry condition that's fixed and known at deploy time (per the spec's explicit assumption) needs no runtime signaling path; this would add complexity (and policy-engine/SDK surface) solely to re-derive something already knowable when the route is compiled.

## Decision 3: How the lookup itself is exposed

**Decision**: Extend the existing `PolicyVersionResolver` interface (`pkg/utils/policy_version_resolver.go`) with one additional method, rather than introducing a second, parallel lookup abstraction:

```go
type PolicyVersionResolver interface {
    Resolve(name string) (string, error)
    Definition(name, version string) (*models.PolicyDefinition, bool) // NEW
}
```

**Rationale**: `StaticPolicyVersionResolver` (the sole implementation, constructed in `main.go` from the same `policyDefinitions` map `Resolve` already reads) already holds every `PolicyDefinition` in memory — `Resolve` just doesn't expose the full struct today. Adding one method to the one existing implementation is smaller and more consistent than introducing a second resolver type that every transformer constructor would also need to accept.

**Alternatives considered**: A free function taking the raw `map[string]models.PolicyDefinition` — rejected, since `LLMTransformer` and `RestAPITransformer` (`pkg/transform/restapi.go`) are already built around the resolver abstraction specifically so callers don't need to know how definitions are sourced or keyed; bypassing it with a raw map parameter would be a step backward from that existing design.

**Correction, superseded during implementation (T009/T010)**: this note originally claimed no shared hook point exists between `RestAPITransformer` and `LLMTransformer`, requiring two separate resolver hooks. That was wrong. Tracing `LLMTransformer.Transform`'s full body (`pkg/transform/llm.go`) during implementation showed it converts its LLM/MCP source config into a genuine `api.RestAPI` and calls `t.restTransformer.Transform(tempCfg)` — the exact same `RestAPITransformer.Transform` method, with no separate policy-chain-building logic of its own. One resolver hook, in `restapi.go`'s `buildPolicyChain`/`sdkChainToModel` call site, covers REST, LLM, and MCP routes alike. `applyModelFailoverPolicyToRoutes` runs afterward and only adds `RouteFailover`, never touching retry contributions. See tasks.md T009/T010 for the as-implemented account, including a real major-vs-full-semver lookup bug this single hook point surfaced and fixed.

## Decision 4: Merge semantics across multiple contributing policies (and with `model-failover`)

**Decision**: Per spec FR-005/SC-004 — union of retryable status codes, OR of connection-failure opt-in (if any contributor sets it, it's on), `MaxAttempts` = **max** across all contributors (including `model-failover`'s own existing chain-derived value when present), translated to Envoy's `NumRetries` via `−1` exactly once at the merge boundary. `PerAttemptTimeoutMs` is the one exception to "broadest wins" — see Decision 7.

**Rationale**: Union/max is the same "most-permissive wins" merge rule `model-failover` itself already uses in its own duplicate-chain-settings validation (two chains sharing a cluster must agree, flagged as a deploy-time error if they don't) — except here, unlike that case, two policies' retry contributions are never semantically contradictory the way two different `suspendDuration`s on one shared cluster would be, so a silent union is correct rather than needing a validation error. `model-failover`'s own retry fields on `RouteFailover` are treated as exactly one more contribution into the same merge, which is what makes the "coexist without special-casing" requirement (spec FR-007) hold structurally rather than by convention.

**Alternatives considered**: Treating `model-failover`'s existing retry construction as authoritative and simply ignoring other contributions when a failover chain is present — rejected outright; it directly violates spec FR-007 (a route combining both must not silently drop either mechanism's coverage), and was the explicit motivating edge case in the spec's User Story 2.

## Decision 5: Field naming — `retry`, not `upstreamRetryOn`

**Decision**: The policy-definition-level block is named `retry` (Go: `Retry`), not the originally-proposed `upstreamRetryOn`. Field names inside it favor plain, capability-oriented vocabulary (`maxAttempts`, `perAttemptTimeoutMs`, `alsoRetryOnConnectionFailure`) over Envoy's own internal `retry_on`/`num_retries` jargon.

**Rationale**: `retry` reads as a capability declaration ("this policy is able to cause a retry") independent of which layer eventually acts on it, which is both clearer to a policy author who doesn't necessarily know Envoy's vocabulary and still unambiguous next to `oauth2-generator`'s own internal `resilientTokenSource.fetchWithRetry` Go method — the two never appear in the same document (one is YAML in `policy-definition.yaml`, the other is a private Go identifier), so the disambiguation concern the original `upstream` prefix was chosen for doesn't actually require that specific word; `retry` alone resolves it just as well by being a definition-level YAML key, not a bare word that could be mistaken for config at all. `maxAttempts` (total sends, first included) was chosen over `numRetries` specifically because Envoy's own `RetryPolicy.NumRetries` field excludes the first send — forcing a policy author to remember and apply that off-by-one themselves would be a recurring, easy-to-get-wrong tax on every policy adopting this contract. The translation is instead centralized once, at the point the merged value is written into Envoy's actual `RetryPolicy` (data-model.md's Merged Route Retry Policy section) — every policy author-facing number means exactly what it says.

**Alternatives considered**: Keeping `upstreamRetryOn`/`numRetries`/`retryOn` to mirror Envoy's own field names one-to-one — rejected; optimizing for "a reader who already knows Envoy config recognizes the vocabulary instantly" is the wrong audience to optimize for, since the actual audience is a policy author who may never otherwise touch raw Envoy configuration, and for whom "how many times total will this go out" is the natural question, not "how many retries beyond the first does Envoy's internal counter track."

## Decision 6: Supporting both a fixed value and a param-derived value, per field

**Decision**: Every field in `Retry` except `enabledByParam` itself supports two mutually-exclusive forms: a fixed literal (`statusCodes`, `maxAttempts`, `perAttemptTimeoutMs`, `alsoRetryOnConnectionFailure`) or a derived reference to one of that same policy's own declared params (`statusCodesFromParam`, `maxAttemptsFromParam`, `perAttemptTimeoutMsFromParam`, `alsoRetryOnConnectionFailureFromParam`), resolved per-attachment at transform time by reading that instance's actual configured value for the named param. See data-model.md for the full shape and resolution order.

**Rationale**: A fixed-only design is correct for oauth2-generator's own 401 case specifically — a true domain constant, invariant across every deployment — but doesn't hold for every policy that might adopt this contract. A policy whose retry-worthy condition is *itself* deployment-dependent (the clearest case: a policy fronting multiple possible backend types, where "what status code means rate-limited" varies by which backend an operator pointed it at) has no single fixed value that's correct for every attachment. Forcing such a policy into the fixed-only form would either be wrong for some deployments, or push the policy author back toward exactly the attachment-level `retry:` config block the original design explicitly rejected — reintroducing the same drift risk that rejection was meant to avoid, just at a different layer. Supporting both forms, chosen per-field by whoever authors that specific policy's definition, lets each policy's author pick whichever is actually true of their own domain, without reopening either previously-rejected design.

**Alternatives considered**:
- *Derived-only (drop the fixed form entirely, always reference a param).* Rejected: would force every policy, including oauth2-generator, to declare a redundant param (e.g., a `retryStatusCode` param that only ever holds `401`) purely to satisfy the schema — adding configuration surface for a value that can never meaningfully change, the opposite of this feature's own goal.
- *A single generic `source: "fixed" | "param"` discriminator field instead of a `...FromParam` suffix per field.* Rejected: a discriminator shared across all conditions can't express "status codes come from a param, but attempt count is fixed" — a real, expected combination. Per-field `...FromParam` suffixes allow any mix, which a single shared discriminator cannot.
- *Let the derived form silently fall back to the fixed form's value when both might apply.* Rejected: the two are defined as mutually exclusive (data-model.md Validation Rule 1) specifically so there is never an ambiguous "which one wins" question to silently resolve one way.

## Decision 7: `perAttemptTimeoutMs` merges by taking the **tightest** value, not the loosest

**Decision**: Unlike every other field (union or max — broadest wins), merging `PerAttemptTimeoutMs` across contributors takes the **minimum** of every contributor's resolved value (ignoring contributors that left it unset).

**Rationale**: Per-try timeout is a single, shared, route-level ceiling in Envoy — it isn't scoped per-policy at dial time, so whichever value the merge picks applies to *every* attempt on the route, not only the attempt where the contributor that requested it actually matters. Taking the loosest (max) value — this plan's original position before this revision — means one contributor with a legitimately slow corrective action (e.g., a 2000ms token refresh) silently lengthens the per-attempt budget for every other contributor's retries too. Combined with a route's overall request timeout, a long per-attempt budget can consume most or all of that overall budget on a single slow attempt, leaving no time left for a *different* contributor's otherwise-fast retry to ever get dispatched — the broadest contributor starves every other contributor's retry chance, not just its own. Taking the tightest value instead guarantees every contributing policy's retry gets a chance to actually fire within the route's overall budget; the tradeoff — a contributor whose own corrective action is slower than the tightest declared ceiling may have that specific attempt cut off before its fix completes — is the lesser failure mode, and is also self-correcting (that contributor's own retry logic sees the resulting response/timeout exactly like any other retryable failure, and gets to try again on the next attempt within `maxAttempts`).

**Alternatives considered**:
- *Max (this plan's original position).* Reverted for the starvation reason above, once the route-level-not-per-policy scope of Envoy's `PerTryTimeout` was made explicit.
- *Reject the deploy if contributors disagree, forcing the operator to resolve it explicitly.* Rejected as disproportionate: unlike `allowCredentials`-style CORS misconfigurations (`go-cors-validation.md`) where a wrong merge is a security defect, a suboptimal per-try timeout is a performance tradeoff, not a correctness/security one — a silent, well-reasoned default (tightest) is appropriate per this feature's own "always additive, never a new required decision for the operator" design goal (spec FR-006).

## Decision 8: `enabledByParam` and `maxAttemptsFromLongestList`

**Decision**: Add `enabledByParam` (names a boolean param that gates the whole contribution on/off per attachment) and a third `maxAttempts` mode, `maxAttemptsFromLongestList` (derives the attempt count from the length of one of the policy's own list-shaped params, plus a constant).

**Rationale**: `enabledByParam` closes a real gap the original design left open: every prior version of this contract was unconditionally active the moment a policy declared `retry` at all, with no way for an operator to opt a specific attachment out short of not attaching the policy. Tying activation to an existing (or policy-author-added) boolean param — never a new retry-specific field an operator fills in — keeps the "no new operator-facing retry config" guarantee (contracts/policy-definition-schema.md guarantee 2) intact while still giving operators a real off-switch where a policy author judges one is warranted. `maxAttemptsFromLongestList` exists because not every policy's natural attempt count is a plain number or a simple param — `model-failover`'s own retry count is really "one attempt per member of my fallback chain," a property of a *list's length*, not a number anyone configures independently of that list. Without this mode, unifying `model-failover`'s own retry-policy construction into this same generic contribution mechanism (noted as explicitly deferred/future work in spec.md) would have no way to express its actual derivation rule; with it, that future unification has a concrete, already-designed path, even though executing it remains out of this feature's scope.

**Alternatives considered**:
- *Require `model-failover` (and any future chain-shaped policy) to pre-compute and expose a separate plain-integer param just for this purpose.* Rejected: duplicates information the list param already carries, and reintroduces exactly the drift risk (two sources of truth that can disagree) this entire feature exists to avoid elsewhere.
- *Make `enabledByParam` apply per-field instead of to the whole `retry` block.* Rejected as unnecessary complexity: no motivating case surfaced for "this policy's status codes are active but its attempt count isn't" — a contribution is either meaningful for this attachment or it isn't, as a whole.
