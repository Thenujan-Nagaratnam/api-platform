## 1. Why AI Readiness Is a New Dimension

For the last fifteen years, "good API design" meant writing for a human developer: readable error messages, interactive Swagger UI, code samples in multiple languages. The mental model was always a person at a terminal, iterating in real time, googling when confused.

That model is no longer complete.

A growing fraction of API traffic is now generated by AI agents — systems that autonomously discover endpoints, parse documentation, handle errors without human review, and retry failures according to their own logic. Cloudflare reported that automated bot traffic surpassed human traffic for the first time in 2024, and RAG-based agent traffic surged 49% in early 2025. When a developer asks Cursor, Copilot, or Claude to "add Stripe payments," the agent fetches documentation, selects APIs, writes integration code, and debugs errors — often before the developer reads a single line.

This creates a new axis of quality: **AI Readiness** — how well a spec equips an LLM to plan, select, and invoke operations without human guidance.

Critically, 75% of production APIs have endpoints that don't match their specs (APIContext, 2024). API drift is the silent enemy of AI readiness: a spec that's correct and complete when shipped becomes a liability as it diverges from the actual service. AI Readiness scores should reflect spec fidelity as much as spec quality.

## 2. How Agents Consume APIs vs. Humans

Understanding the fundamental differences in how agents and humans interact with APIs is the foundation for every rule in this framework.

### 2.1 Discovery: Semantic Search vs. Visual Browsing

**Humans** browse documentation, skim endpoint lists, and use Ctrl+F. They infer intent from URLs, examples, and prose descriptions. They tolerate vague names because they can cross-reference and ask questions.

**Agents** perform semantic matching against a spec loaded entirely into context. When an agent decides which endpoint to call, it's doing something close to vector search against your descriptions. The quality of your `summary` and `description` fields directly determines whether the agent routes to the correct endpoint. `"Gets the data"` loses to `"Returns a paginated list of invoices filtered by status and date range, sorted by created_at descending. Requires accounting:read scope."` every time.

### 2.2 Context Window: Bulk Processing vs. Incremental Reading

This is the most important structural difference.

**Humans** read documentation serially and interactively. They open one endpoint, understand it, then move on. They hold state in their head across sessions.

**Agents** receive the entire spec (or a large slice of it) injected into their context window at once. This creates two critical problems:

1. **Token pressure.** Every redundant character, every empty description field, every duplicated schema, consumes tokens that could be used for reasoning. When planning accuracy for agents was tested against 300+ endpoints, accuracy dropped to ~30-49% — heavy specs degrade agent performance measurably (Orbital, 2026).
2. **Disambiguation load.** If 20 operations have similar names or missing descriptions, the agent must infer their differences from structure alone. This dramatically increases hallucination risk — agents have been observed calling non-existent endpoints when descriptions were inadequate.

**Implication:** AI Readiness rewards specs that are dense with signal and lean on noise.

### 2.3 Tool Selection: Pattern Matching vs. Contextual Judgement

**Humans** use contextual judgement shaped by experience. They recognize `POST /users/bulk-delete` as a destructive batch operation by combining their knowledge of HTTP verbs, resource naming, and the word "bulk."

**Agents** rely on the structured signal in the spec. The `operationId` becomes the function name in tool-calling frameworks. The `summary` becomes the one-line description an LLM reads to decide whether to invoke it. Missing or generic `operationId` values force agent frameworks to auto-generate names from method + path — producing machine-readable but semantically poor names like `post_users_bulk_delete`.

Google's Agent Development Kit (ADK) explicitly derives tool names from `operationId` (converted to snake_case, capped at 60 characters) and uses `summary` or `description` as the tool description fed to the LLM. This is representative of how all major agentic frameworks (LangChain, Haystack, Semantic Kernel, LangGraph) consume OpenAPI specs.

### 2.4 Error Handling: Interactive Debugging vs. Autonomous Recovery

**Humans** read error messages, consult documentation, and decide how to fix a problem. They can ask for help.

**Agents** must parse error responses programmatically and decide to retry, bail out, or try an alternative. An error response that contains only `{"message": "bad request"}` provides no signal for recovery. An error with a machine-readable `code`, a `field`-level breakdown, and a `documentation` link allows an agent to self-correct without human intervention.

### 2.5 State Management: Session Awareness vs. Stateless Reasoning

**Humans** hold state across multiple calls: "I just created user 123, now let me create an order for them." They naturally thread IDs through workflows.

**Agents** can also maintain state, but they rely on the spec to communicate which response fields map to which request fields in downstream calls. Without explicit linkage — either through well-named response properties (`userId` that maps to an `orderId` parameter's description: "The user ID returned from POST /users") or through workflow-level specs like Arazzo — agents must infer these connections from naming alone, which is error-prone.

### 2.6 Retry Behavior: Considered vs. Mechanical

**Humans** don't double-submit a payment form unless they mean to. They understand consequences.

**Agents** retry aggressively. Network timeouts, rate limits, and transient 5xx errors will all trigger automatic retry logic. If your mutating endpoints (`POST`, `PATCH`, `DELETE`) are not idempotent and your spec doesn't communicate this clearly, agents can cause duplicate charges, duplicate records, or cascading deletions. This is not a spec quality problem in isolation — but the spec is the right place to declare idempotency support (via headers like `Idempotency-Key`) so agents know they can retry safely.

## 3. The Five Pillars of AI Readiness

### Pillar 1: Semantic Clarity

*Can the agent understand what each operation does, what it expects, and what it returns — without running it?*

This pillar governs the quality of natural-language annotations in the spec. It is the highest-leverage area: poor descriptions are the single most common reason agents hallucinate endpoints or call the wrong operation.

**Key signals:**
- `operationId` is present, unique, and semantically meaningful (not auto-generated)
- Every operation has a `summary` (concise, action-oriented)
- Every operation has a `description` that explains intent, side effects, required scopes, and edge cases
- Every parameter has a `description` explaining its purpose and valid values
- Enum values have descriptions (not just the values themselves)
- Request body fields have descriptions
- Response schema properties have descriptions
- The `info.description` explains the API's domain and primary use cases

**Anti-patterns:**
- `operationId: "get_api_v1_users_id_get"` (auto-generated from path)
- `summary: "Get user"` with no `description`
- Parameters named `type`, `kind`, or `mode` without explaining what each valid value means
- Enum values like `["1", "2", "3"]` with no documentation of what each means

### Pillar 2: Schema Precision

*Are the data types and structures precisely enough defined that an agent can construct valid requests and parse responses without guessing?*

LLMs struggle with ambiguous types. A field that can be a string, number, or null requires the agent to infer which form to use in a given context. Schema ambiguity is the primary driver of incorrect parameter values in tool-calling scenarios.

**Key signals:**
- All properties have explicit `type` declarations (no implicit typing)
- No use of bare `additionalProperties: true` on request bodies (hides required structure)
- Required fields are explicitly declared in `required` arrays
- Nullable fields use `nullable: true` or `anyOf: [type, null]` explicitly rather than implicitly
- Date/time fields use `format: date-time` (not plain strings)
- ID fields have consistent types across the spec (always string UUIDs, or always integer IDs — never mixed)
- Enums are properly typed and exhaustively listed
- Response schemas are defined for all success codes (not just `200`)
- Error response schemas are consistent across all endpoints (see Pillar 3)
- `$ref` components are used for shared schemas (reduces token duplication and aids consistency)
- No `oneOf`/`anyOf` without `discriminator` where the distinction matters for input construction

**Anti-patterns:**
- `type: object` with no `properties` defined
- Response schema defined for `200` but not `201` (common in POST operations)
- Mixed ID formats (some endpoints return `id` as integer, others as string)
- `format` missing on binary, date, or UUID fields

### Pillar 3: Agent Behavioral Compatibility

*Does the API support the behavioral patterns agents depend on for reliable, autonomous operation?*

This pillar addresses the runtime contract between the API and an agent. It's not just about spec quality — it's about whether the spec *communicates* the safety guarantees agents need to operate autonomously.

**Key signals:**

**Idempotency**
- Mutating operations (`POST`, `PATCH`) that could be retried declare support for `Idempotency-Key` header in their parameter list
- The spec describes what happens on duplicate key submission (returns original response with same status code, or `409 Conflict` if called with different body)
- Idempotency behavior is documented in the operation `description`

**Pagination**
- List endpoints use cursor-based pagination (not offset/page-number), which is stable under concurrent insertions/deletions — critical for agents traversing large datasets
- Pagination parameters are consistently named across all list endpoints (`cursor`, `limit` or `pageSize`)
- Response envelopes include `has_more` / `next_cursor` fields with clear schema definitions
- The spec documents the maximum `limit` value and behavior at the end of the list
- Agents need to traverse complete datasets without gaps or duplicates; offset pagination breaks when items are added/deleted mid-traversal

**Error Response Consistency**
- All endpoints return errors in the same schema (machine-parseable `code`, human-readable `message`, field-level `details`, `request_id`)
- The spec uses RFC 7807 Problem Details format or equivalent structured schema
- Error codes are documented as enum values with descriptions
- The spec distinguishes between retryable errors (5xx, 429) and non-retryable errors (400, 422) in the description
- `429` responses include `Retry-After` header in the response schema
- Retry guidance is documented in the operation description or `info.description`

**Rate Limiting**
- Rate limit headers (`X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`) are declared in response schemas
- The spec documents the rate limit policy (per-minute, per-day, per-key)

**Bulk Operations**
- For APIs with many resources, bulk read/write operations exist (e.g., `POST /users/bulk`, `GET /users?ids[]=1&ids[]=2`)
- Agents process tasks in parallel and benefit from batching; single-item-only APIs force N individual calls
- Bulk response schema identifies per-item success/failure independently

**Destructive Operation Safety**
- `DELETE` operations include description of cascading effects
- Irreversible operations are flagged in their description
- Where applicable, soft-delete vs. hard-delete behavior is documented

### Pillar 4: Spec-Level Completeness

*Is the spec complete enough to be consumed without referencing external documentation?*

An agent has no ability to "just check the documentation website" when something is unclear. The spec must be entirely self-contained.

**Key signals:**
- `info.title` and `info.description` clearly identify what the API does
- `info.version` is present and follows semantic versioning
- `servers` array is present with at least one concrete URL (not a placeholder)
- Security schemes are fully defined (`securitySchemes` in components)
- Every operation declares its applicable `security` requirements (or inherits a global one)
- Authentication parameters (headers, query params) are documented with their format
- `tags` group operations logically (an agent can use tags to narrow context window selection)
- Tag objects include `description` fields
- `externalDocs` links point to canonical references where needed
- The spec validates against the OpenAPI 3.x schema without errors

**Anti-patterns:**
- `servers: [{"url": "https://example.com"}]` (placeholder URL)
- Security schemes declared but not applied to operations
- `$ref` pointers to undefined components (broken references)
- Operations with no `tags` that belong to a large spec

### Pillar 5: Workflow Expressibility

*Can the agent understand multi-step workflows that span multiple operations?*

The most advanced readiness dimension. Individual operation quality is necessary but not sufficient for complex agentic workflows. Agents executing multi-step tasks — "book a flight, add it to my calendar, send a confirmation email" — must infer how operation outputs chain into operation inputs. When this linkage is implicit, agents hallucinate or fail.

**Key signals:**
- Response property names semantically match parameter names they feed into (e.g., a `POST /orders` response property named `orderId` matches a `GET /orders/{orderId}` path parameter)
- The Arazzo Specification (OpenAPI Initiative, 2024) is used to explicitly define sequences of calls, their dependencies, and data flow — turning an endpoint list into a workflow definition
- Operation descriptions include "next steps" guidance (e.g., "After creating a user, call POST /users/{userId}/verify to send a verification email")
- `links` objects in responses define how output fields map to downstream operation parameters (OpenAPI 3.x native feature)
- Webhook schemas are defined where the API supports async patterns
- Long-running operations expose a polling pattern (`202 Accepted` + `GET /jobs/{jobId}`) with the polling endpoint clearly linked from the initiating operation's description

**Arazzo (OpenAPI 2024+)**

The Arazzo Specification is a complementary standard released in May 2024 that allows an API producer to define explicit multi-step workflows. Rather than a list of endpoints, Arazzo describes sequences of calls, how responses feed into subsequent requests, conditional branching, and the expected outcome. For agentic use cases, a spec with Arazzo workflows is substantially more AI-ready than one without, because the agent doesn't need to infer the correct sequence — it's declared.

## 4. Scoring Model

### 4.1 Suggested Weights

| Pillar | Weight | Rationale |
|--------|--------|-----------|
| Semantic Clarity | 35% | Highest direct impact on tool selection accuracy |
| Schema Precision | 25% | Drives correct parameter construction |
| Agent Behavioral Compatibility | 20% | Critical for autonomous, reliable operation |
| Spec-Level Completeness | 15% | Foundation — incomplete specs fail before anything else |
| Workflow Expressibility | 5% | Advanced; valuable but less broadly applicable |

### 4.2 Rule Severity Levels

Each rule in the rule catalogue should carry a severity that shapes the score and feedback:

| Severity | Label | Impact |
|----------|-------|--------|
| 🔴 Critical | Must fix | Blocks agent from using the operation at all |
| 🟠 High | Should fix | Causes frequent agent errors or hallucinations |
| 🟡 Medium | Consider fixing | Degrades agent reliability or efficiency |
| 🟢 Low | Improvement | Nice to have; improves token efficiency or discoverability |

### 4.3 Score Calculation

```
pillar_score = (rules_passed × rule_weight) / total_possible_weight

overall_score = Σ (pillar_score × pillar_weight)
```

Display as 0–100 with a letter grade:

| Score | Grade | Label |
|-------|-------|-------|
| 90–100 | A | Agent-native |
| 75–89 | B | Agent-ready |
| 60–74 | C | Needs improvement |
| 40–59 | D | Significant gaps |
| 0–39 | F | Not agent-ready |

### 4.4 Endpoint-Level Scores

In addition to the overall score, display a per-endpoint score so developers can prioritize the most impactful endpoints first. Surface the top 5 lowest-scoring endpoints as priority recommendations.

## 5. Rule Catalogue with Examples

Below is a structured catalogue of rules for implementation. Each rule includes the check, severity, feedback message template, and a before/after example.

---

### PILLAR 1 — Semantic Clarity

---

#### SC-01 — `operationId` Present and Meaningful
**Severity:** 🔴 Critical

**Check:** Every operation has an `operationId`. It is not auto-generated from path/method (i.e., does not match the pattern `{method}_{path_segments}`). It uses camelCase or snake_case consistently.

**Why it matters:** Agent frameworks (Google ADK, LangChain, Semantic Kernel) derive function/tool names directly from `operationId`. Auto-generated IDs like `get_api_v2_invoices_invoice_id_get` are semantically meaningless to an LLM choosing among 50 tools.

**Feedback:** `"operationId '{id}' appears to be auto-generated. Replace with a descriptive name like 'getInvoiceById' that an AI agent can use to identify the operation's purpose."`

**Before:**
```yaml
/invoices/{invoiceId}:
  get:
    operationId: get_api_v2_invoices_invoice_id_get
```

**After:**
```yaml
/invoices/{invoiceId}:
  get:
    operationId: getInvoiceById
    summary: Get a single invoice by ID
    description: >
      Returns the full invoice record including line items, tax, and payment status.
      Requires the 'billing:read' scope.
```

---

#### SC-02 — `summary` Present on All Operations
**Severity:** 🟠 High

**Check:** Every operation has a non-empty `summary` field of 10–80 characters that is action-oriented (starts with a verb: Get, List, Create, Update, Delete, Search, etc.).

**Why it matters:** The `summary` is the one-line description used by agent frameworks to populate the tool description shown to the LLM during tool selection.

**Feedback:** `"Operation '{operationId}' is missing a summary. Add a concise, action-oriented summary like 'List invoices filtered by status and date range'."`

---

#### SC-03 — `description` Present and Substantive on Operations
**Severity:** 🟠 High

**Check:** Every operation has a `description` of at least 30 characters. It includes: (a) what the operation does, (b) any preconditions or required scope/permissions, (c) notable side effects or limits.

**Feedback:** `"Operation '{operationId}' has a very short description ('{desc}'). Expand it to include preconditions, required scopes, and edge cases. This is the primary signal agents use for routing."`

---

#### SC-04 — All Parameters Have Descriptions
**Severity:** 🟠 High

**Check:** Every parameter (`in: path`, `in: query`, `in: header`, `in: cookie`) has a non-empty `description`.

**Feedback:** `"Parameter '{name}' on '{operationId}' has no description. Explain what value to provide, valid formats, and any constraints (e.g., 'The invoice ID returned from POST /invoices. Must be a UUID v4.')."`

---

#### SC-05 — Enum Values Are Documented
**Severity:** 🟡 Medium

**Check:** Properties and parameters with `enum` values have either (a) a `description` that explains each enum value's meaning, or (b) use `x-enumDescriptions` extension.

**Before:**
```yaml
status:
  type: string
  enum: [pending, active, suspended, closed]
```

**After:**
```yaml
status:
  type: string
  enum: [pending, active, suspended, closed]
  description: >
    The account lifecycle state.
    - pending: Account created but email not verified
    - active: Account in good standing
    - suspended: Account suspended by admin action
    - closed: Account permanently closed; data retained for 90 days
```

---

#### SC-06 — Request Body Properties Have Descriptions
**Severity:** 🟡 Medium

**Check:** At least 80% of request body schema properties have descriptions.

---

#### SC-07 — `info.description` Present and Descriptive
**Severity:** 🟡 Medium

**Check:** `info.description` is at least 100 characters and explains the API's purpose, primary use cases, and target domain.

**Why it matters:** An agent loading a large spec often reads `info.description` first to orient itself. A one-sentence or missing description provides no orientation for a multi-step planning task.

---

### PILLAR 2 — Schema Precision

---

#### SP-01 — No Untyped Object Properties
**Severity:** 🔴 Critical

**Check:** No request body properties or response properties that are `type: object` without a `properties` definition (unless `additionalProperties` with a typed schema is used intentionally).

**Feedback:** `"Schema '{name}' is an untyped object. Define its properties explicitly so agents can construct valid request bodies without guessing."`

---

#### SP-02 — Required Fields Explicitly Declared
**Severity:** 🔴 Critical

**Check:** Request body schemas declare `required` arrays. No required fields inferred from descriptions alone.

---

#### SP-03 — Response Schemas Defined for All Success Codes
**Severity:** 🟠 High

**Check:** Every operation defines response schemas for all its success codes (`200`, `201`, `202`, `204`). A `204` with no body is acceptable.

**Why it matters:** Agents parse response bodies to extract IDs and values needed for downstream calls. An undefined response schema means the agent must guess at the structure.

---

#### SP-04 — Consistent ID Field Types
**Severity:** 🟠 High

**Check:** ID fields are typed consistently across the entire spec. Either all IDs are `type: string` (UUIDs) or all are `type: integer` — no mixing.

---

#### SP-05 — Date/Time Fields Use `format`
**Severity:** 🟡 Medium

**Check:** Fields representing dates or timestamps have `format: date`, `format: date-time`, or `format: time` declared.

---

#### SP-06 — Shared Schemas Use `$ref`
**Severity:** 🟡 Medium

**Check:** Identical schema structures defined inline in more than one location. Should be extracted to `components/schemas` and referenced.

**Why it matters:** Inline duplication increases token count and introduces drift risk. An agent receiving a 50KB spec has less reasoning capacity for a 100KB spec of equivalent logical content.

---

#### SP-07 — `oneOf`/`anyOf` Uses `discriminator`
**Severity:** 🟡 Medium

**Check:** Any `oneOf` or `anyOf` used for request bodies declares a `discriminator` property.

**Why it matters:** Without a discriminator, an agent must attempt to match the correct variant by trial-and-error, leading to higher error rates on polymorphic endpoints.

---

### PILLAR 3 — Agent Behavioral Compatibility

---

#### AB-01 — Error Response Schema Is Consistent
**Severity:** 🔴 Critical

**Check:** All error responses (`4xx`, `5xx`) across all endpoints reference the same `$ref` error schema. The schema includes at minimum: `code` (string enum), `message` (string), `request_id` (string).

**Why it matters:** Agents need to parse errors uniformly. If each endpoint returns errors in a different structure, an agent must maintain endpoint-specific error parsing logic — which is not feasible in a dynamic tool-calling context.

---

#### AB-02 — `429` Response Declares `Retry-After`
**Severity:** 🟠 High

**Check:** Any operation that can return `429 Too Many Requests` declares a `Retry-After` response header in its `429` response schema.

**Why it matters:** Without `Retry-After`, an agent retrying a rate-limited call uses exponential backoff with jitter (at best) or hammers the endpoint blindly (at worst). Declaring the header enables intelligent retry behavior.

---

#### AB-03 — Idempotency Key Support Declared for Mutating Operations
**Severity:** 🟠 High

**Check:** `POST` operations that create resources or have financial/state-change side effects declare an `Idempotency-Key` request header parameter. The description explains the behavior on duplicate submission.

**Before:** `POST /payments` with no idempotency declaration.

**After:**
```yaml
parameters:
  - name: Idempotency-Key
    in: header
    required: false
    schema:
      type: string
      format: uuid
    description: >
      Optional client-generated UUID. If provided, the server guarantees that
      submitting the same key twice returns the original response without
      processing the payment a second time. Returns 409 if the same key is
      submitted with a different request body.
```

---

#### AB-04 — List Endpoints Use Cursor-Based Pagination
**Severity:** 🟠 High

**Check:** Endpoints returning collections use `cursor` + `limit` parameters rather than `page` + `per_page` (offset pagination). Response includes `has_more` and `next_cursor` fields.

**Why it matters:** Agents traverse datasets from start to finish. Offset pagination is unstable when records are inserted or deleted mid-traversal; agents on page 3 of a shifting dataset will miss or duplicate records.

---

#### AB-05 — Pagination Parameters Are Consistently Named
**Severity:** 🟡 Medium

**Check:** All list endpoints use the same parameter names for pagination controls. Inconsistency (some use `cursor`, some use `page_token`, some use `after`) forces agents to learn per-endpoint patterns.

---

#### AB-06 — Bulk Operations Available for High-Volume Resources
**Severity:** 🟡 Medium

**Check:** For resources that appear in list endpoints with pagination, a bulk read endpoint exists (e.g., `GET /users?ids[]=1&ids[]=2` or `POST /users/batch`).

**Why it matters:** Agents executing tasks like "update all overdue invoices" would need to issue hundreds of individual PATCH calls without a bulk endpoint. This is both slow and likely to hit rate limits.

---

#### AB-07 — Destructive Operations Are Clearly Labeled
**Severity:** 🟡 Medium

**Check:** `DELETE` operations, and any `POST`/`PATCH` operations with irreversible side effects, include a `description` note on irreversibility and cascading effects (e.g., "Permanently deletes the user and all associated orders. This action cannot be undone.").

**Why it matters:** Agents do not have the same hesitation a human has before clicking "Delete." A spec that clearly labels irreversible operations allows agent orchestrators to implement confirmation gates.

---

#### AB-08 — HTTP Status Codes Are Correct and Specific
**Severity:** 🟠 High

**Check:** Operations use semantically correct status codes:
- `POST` creating a resource returns `201` (not `200`)
- `DELETE` with no body returns `204` (not `200`)
- Validation errors return `422` (not `400`)
- Authentication failures return `401` (not `403`)
- Authorization failures return `403`

**Why it matters:** Agents use status codes to decide whether to retry, bail, or self-correct. Incorrect status codes send agents down the wrong recovery path.

---

### PILLAR 4 — Spec-Level Completeness

---

#### SL-01 — Spec Validates Against OpenAPI Schema
**Severity:** 🔴 Critical

**Check:** The spec passes validation against the OpenAPI 3.x JSON schema with no errors. Warnings are allowed.

**Why it matters:** Invalid specs cause agent frameworks to fail to parse or silently drop operations.

---

#### SL-02 — `operationId` Values Are Globally Unique
**Severity:** 🔴 Critical

**Check:** No two operations in the spec share an `operationId`.

**Why it matters:** Duplicate `operationId` values cause agent frameworks to either fail or silently drop one of the operations. This is one of the most common spec defects (Speakeasy, 2023).

---

#### SL-03 — Server URL Is Concrete
**Severity:** 🟠 High

**Check:** The `servers` array contains at least one entry with a URL that is not a placeholder like `https://example.com` or `https://api.yourservice.com`.

---

#### SL-04 — Security Schemes Are Applied to Operations
**Severity:** 🟠 High

**Check:** If `securitySchemes` are defined, they are applied either globally (`security` at the root level) or per-operation. Operations with no security declared are flagged unless the spec explicitly intends them to be public.

---

#### SL-05 — All Operations Have Tags
**Severity:** 🟡 Medium

**Check:** Every operation has at least one `tag`. Tags group related operations and allow agent frameworks to selectively load only the relevant slice of a large spec into context.

---

#### SL-06 — Tag Objects Have Descriptions
**Severity:** 🟡 Medium

**Check:** All tags used in operations are declared as tag objects in the root `tags` array with `description` fields.

---

#### SL-07 — No Broken `$ref` Pointers
**Severity:** 🔴 Critical

**Check:** All `$ref` values resolve to a defined component in the spec.

---

#### SL-08 — No Orphaned Components
**Severity:** 🟢 Low

**Check:** All schemas, parameters, and responses defined in `components` are referenced at least once.

---

### PILLAR 5 — Workflow Expressibility

---

#### WE-01 — Response Properties Semantically Link to Downstream Parameters
**Severity:** 🟡 Medium

**Check:** For operations that return IDs intended for use in subsequent calls, the response property name matches (or is described as matching) the path/query parameter name in the downstream operation.

**Example:** `POST /orders` returns `{ "orderId": "..." }` and `GET /orders/{orderId}` uses `orderId` as its path parameter — semantically linked.

**Counter-example:** `POST /orders` returns `{ "id": "..." }` but downstream uses `orderId` — an agent must infer the mapping.

---

#### WE-02 — OpenAPI `links` Objects Defined for Key Workflows
**Severity:** 🟢 Low

**Check:** At least the most critical cross-operation workflows use OpenAPI 3.x `links` objects in response definitions to explicitly declare how response values map to downstream operation parameters.

```yaml
responses:
  '201':
    description: Order created
    content: ...
    links:
      GetOrderById:
        operationId: getOrderById
        parameters:
          orderId: '$response.body#/orderId'
```

---

#### WE-03 — Long-Running Operations Use Documented Polling Pattern
**Severity:** 🟡 Medium

**Check:** Operations returning `202 Accepted` include in their `description` the polling endpoint to check status, and the polling endpoint links back to the initiating operation.

---

#### WE-04 — Arazzo Workflow Document Exists
**Severity:** 🟢 Low

**Check:** For APIs with complex multi-step workflows, an Arazzo Specification document exists alongside the OpenAPI spec.

**Note:** This is an advanced check. Flag as an "opportunity" rather than a deficiency for most specs.

## 6. Extension Architecture Recommendations

### 6.1 Rule Engine

Implement the rule engine as a pipeline of stateless rule functions, each taking the parsed spec and returning a `RuleResult`:

```typescript
interface RuleResult {
  ruleId: string;
  severity: 'critical' | 'high' | 'medium' | 'low';
  pillar: string;
  passed: boolean;
  message: string;
  location?: string; // JSON Pointer, e.g. "/paths/~1invoices/{invoiceId}/get"
  suggestion?: string;
  example?: { before: string; after: string };
}
```

### 6.2 Spec Parsing

Use a validated parser like `@scalar/openapi-parser` (supports 2.0, 3.0, 3.1, 3.2) or `openapi3-ts` to normalize the spec before running rules. Dereference `$ref` pointers before applying schema-level rules.

### 6.3 Score Display

Show scores at three levels simultaneously:
1. **Overall score** (0–100 with letter grade)
2. **Pillar scores** (radar/spider chart is ideal for showing balance)
3. **Per-endpoint scores** (sortable table; surface worst-scoring endpoints first)

### 6.4 Inline Diagnostics

Integrate rule results as VS Code `Diagnostic` entries so violations appear as squiggly underlines at the exact line in the YAML/JSON file. Map each `RuleResult.location` (JSON Pointer) to a line range using the parsed spec's source map.

### 6.5 Quick Fix Code Actions

For auto-fixable rules (missing `operationId`, missing `required` flag, inconsistent pagination parameter names), offer VS Code Quick Fix code actions that apply the suggested correction directly.

### 6.6 Progressive Disclosure

Present feedback in two modes:
- **Summary panel**: Pillar scores, top issues, overall grade — visible at a glance
- **Detail panel**: Full rule results with before/after examples, accessible per-rule

### 6.7 Token Estimation

As an advanced feature, estimate the token count of the spec as it would be loaded into an LLM context (using a tokenizer like `tiktoken`). Display this alongside the score as a signal of context window pressure. Specs over 50,000 tokens should trigger a warning because agent accuracy degrades significantly at that scale.
